## 审计发现

### 1. 父分类可挂工具，但父分类在有子分类后无法被选中

涉及文件：

- `/tmp/toolsbox-remote-audit/src/renderer/components/ToolModal.tsx`
- `/tmp/toolsbox-remote-audit/src/renderer/components/Sidebar.tsx`
- `/tmp/toolsbox-remote-audit/src/renderer/components/MainContent.tsx`

问题描述：

- `ToolModal` 注释写的是“只显示叶子分类”，但实际代码只是排除了 `all`，父分类仍然可选
- `Sidebar` 中一旦某个顶级分类有子分类，点击顶级行只会折叠/展开，不能选中该分类
- `MainContent` 的过滤又是严格按 `categoryId === selectedCategoryId` 做的，不会自动包含子分类

结果：

- 如果工具被挂到一个已经拥有子分类的父分类下，这些工具只能在“全部工具”里看见
- 按分类浏览时，这批工具会表现成“消失”

建议：

- 二选一即可：
- 要么 `ToolModal` 只允许选择真正的叶子分类
- 要么允许在 `Sidebar` 里选中父分类，并定义父分类筛选是否包含子分类

### 2. 侧边栏宽度虽然会保存，但应用重启后首次渲染不会恢复

涉及文件：

- `/tmp/toolsbox-remote-audit/src/renderer/components/Sidebar.tsx`

问题描述：

- `width` state 在 `data` 还没加载完成时用默认值 `220` 初始化
- 后续 `data.settings.sidebarWidth` 到位后，没有任何同步逻辑把 state 更新回来

结果：

- 用户拖拽后虽然数据已持久化，但重新打开应用时侧边栏还是先按 `220` 渲染
- 这会让“侧边栏宽度已保存”的功能在体验上失真

建议：

- 在 `data.settings.sidebarWidth` 变化时同步一次 `width`
- 或直接把宽度改成受控值，避免本地 state 和持久化配置分离

### 3. README 已经和最新实现不一致

涉及文件：

- `/tmp/toolsbox-remote-audit/README.md`
- `/tmp/toolsbox-remote-audit/src/shared/types.ts`

问题描述：

- README 仍然写“保留 Windows 和 Linux 兼容能力”
- README 仍然把 `batch`、自定义背景色列为能力
- 但这次远端代码已经明确移除了 `batch` 类型，并把实现改成了 macOS 专用启动逻辑

结果：

- 后续协作者会被文档误导，继续按跨平台或 Windows 兼容方向做判断
- 文档和实际产品边界已经偏离

建议：

- README 里把“兼容目标”改成更谨慎的表述
- 把“已实现能力”改成和代码一致的 macOS 当前能力集
